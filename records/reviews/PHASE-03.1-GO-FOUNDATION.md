## 4. 面试价值

### 主线

我先建立统一的工程边界，再进入业务实现：配置和生命周期保证服务可控，HTTP API 保证输入输出一致，domain/application/adapter 保证业务规则和基础设施可替换，Makefile 保证 AI 生成代码可复现验收。

### 技术深挖点

1. 为什么请求 ID 要进入日志和后续事件；
2. 为什么客户端错误消息和内部 cause 分离；
3. 为什么 application 依赖接口而不是 MySQL 实现；
4. `make check` 通过和业务正确之间有什么区别；
5. 为什么 Room 已有内存 adapter，而 Order/Growth 暂时只有端口。

### 薄弱点

- 主程序入口和 HTTP server 的部分路径覆盖率较低；
- TCP 监听受沙箱限制，尚未完成真实网络集成测试；
- Room/Order/Growth 的完整业务用例尚未实现；
- Makefile 还没有 race、Docker 和 CI job。

## 5. AI 工作流复盘

### 有效做法

- 先给 AI 业务边界和状态机，再生成工程代码；
- 让 AI 同时生成测试和失败路径；
- 遇到工具失败时区分代码问题和环境限制；
- 用固定 `make check` 把 AI 产物纳入统一门禁。

### 需要改进

- 后续生成订单代码前，先明确不变量：订单唯一、扣币幂等、Outbox 不丢；
- 要求 AI 对数据库事务和并发锁给出失败时序，而不是只给 happy path；
- 增加 `go test -race ./...` 和集成测试命令；
- 对覆盖率数字按包和关键路径解读，不追求盲目提高总百分比。

## 6. 计划偏差

原计划将配置、HTTP、分层和工程命令作为骨架任务；实际增加了 Room 内存垂直切片和更完整的 HTTP 测试，但没有引入外部依赖或扩大业务范围。TCP 集成测试因环境限制延后。

## 7. 阶段结论

第 3.1 阶段达到“工程底座可运行、边界可替换、质量命令可复现”的标准，可以进入 Go 并发和领域实现。当前项目的主要风险已经从“没有工程骨架”转移为“业务代码和分布式链路尚未落地”。
