# AI Vibe Coding 工作流日志

## Log 0001：工作区初始化与面试导向设计

日期：2026-09-01

### 用户目标

用 30 天准备字节跳动后端开发实习生（营收增长方向）面试，重点补齐后端项目和 AI 工程能力，并让过程可复盘、可迁移。

### 本次 AI 协作任务

1. 反思原始准备思路是否过窄或不可行；
2. 检查空工作区和可操作文件范围；
3. 建立分层总体计划；
4. 建立项目、日志和上下文备份目录；
5. 执行第一个最低单元。

### AI 做了什么

- 判断“简历引导面试”方向可行，但必须以真实可验证实现为基础；
- 将项目收敛为直播营收增长平台，而不是无边界微服务集合；
- 定义最低单元：一次或少数几次执行、一个主题、明确产物和验收标准；
- 创建工作区文档和 Go 最小项目骨架；
- 探测本地 Go/Git 工具链。

### 人工判断与取舍

- 采用 `project/livegrow` 存放代码，`docs` 存放计划和设计，`records` 存放过程日志与上下文；
- 暂不引入真实外部服务和 API 密钥；
- 先完成订单可靠性主线，再扩展 AI Copilot 和多机房模拟；
- 所有规模指标必须通过本地压测获得。

### 本次亮点

“AI 生成活动候选配置，规则系统负责预算、权限、Schema、灰度和回滚”成为 AI 与后端营收业务的连接点。

### 验收结果

第一次 `go test ./...` 因默认 Go build cache 位于沙箱不可写目录而失败；将 `GOCACHE` 指向允许写入的临时目录后测试通过，`go run ./cmd/livegrow` 输出 `livegrow 0.1.0`。这被记录为环境约束，而不是代码缺陷。

### 可复用经验

AI 最适合辅助拆解、生成样板、补测试和比较方案；核心边界、风险判断、并发安全、一致性和最终验收必须由人负责。

### 下一步

完成 `2.1.1 直播营收业务范围`：一页需求、核心角色、主流程、非目标和成功指标。

## Log 0002：业务范围和一致性边界

日期：2026-09-02

### 用户反馈

用户确认工作区方案，并说明会将项目同步到 GitHub；阶段性成果完成后需要提醒手动 push。

### 本次 AI 协作任务

- 将 LiveGrow 从“技术栈展示项目”收敛为直播间、礼物订单、营收事件和增长实验的业务闭环；
- 明确用户角色、核心流程、强约束与最终一致数据；
- 明确原型的非目标，防止虚构生产能力和范围膨胀；
- 产出后续数据模型和 API 设计的业务基线。

### AI 做了什么

- 创建 `docs/01-BUSINESS-REQUIREMENTS.md`；
- 更新总体计划和当前状态；
- 把“订单可靠受理”和“异步下游完成”拆成两个阶段；
- 把 AI 定位为活动候选配置生成器，而不是账务决策器。

### 人工判断与取舍

- 将真实支付替换为可控的模拟账户服务，避免项目依赖外部系统；
- 账务事实采用强约束/可对账思路，热度和看板允许延迟；
- 多机房只做 region 逻辑模拟和故障演练，不声称真实全球部署；
- 优先订单主链路，运营后台和复杂推荐不进入第一版。

### 面试亮点

“不同数据采用不同一致性等级”比笼统地说“系统保证一致性”更贴近营收业务：订单和扣币不能重复，热度指标可以短暂延迟。

### 验收结果

业务基线文档已创建，包含角色、流程、状态语义、成功指标和非目标范围；后续数据库与 API 设计可以直接引用该文档。

### 下一步

进入 `2.1.2 礼物订单场景`，设计订单状态机和事件模型。

## Log 0003：订单状态机、幂等和补偿

日期：2026-09-02

### 用户反馈

用户确认继续推进，并会手动维护 GitHub 云备份；阶段性成果需要提醒 push。

### 本次 AI 协作任务

- 将礼物购买流程细化为可编码的订单领域；
- 设计订单、支付、发放和 Outbox 的分离状态；
- 明确请求幂等、消息重复消费、重试、死信和对账规则；
- 为后续数据库和 API 设计提供字段与约束输入。

### AI 做了什么

- 创建 `docs/02-ORDER-DOMAIN.md`；
- 将“订单主状态”和“下游阶段状态”拆开，避免一个状态字段表达多个事实；
- 采用本地事务 + Outbox + 至少一次投递 + 幂等消费；
- 加入失败矩阵、对账规则和可直接转成测试的用例清单。

### 人工判断与取舍

- 第一版不引入真实支付和退款，使用模拟 Wallet Service；
- 订单接口定义为“可靠受理”，不承诺同步完成所有异步动作；
- 不追求端到端 Exactly Once，把问题转化为可安全重放；
- 将业务错误与可恢复错误分开，避免无意义重试。

### 面试亮点

订单状态拆分为主状态、支付状态和发放状态后，故障恢复可以定位到具体阶段；Outbox 的 `DEAD` 状态表示自动投递停止，不表示事件被删除，后续仍可通过补偿恢复。

### 验收结果

订单领域文档已创建，包含状态机、事务边界、事件字段、失败矩阵、对账规则和测试清单。

### 下一步

进入 `2.1.3 增长实验场景`，设计活动版本、用户分流、预算约束、灰度和回滚。

## Log 0004：营收增长实验和 AI 护栏

日期：2026-09-02

### 用户反馈

用户确认继续推进；阶段性成果由用户手动 push 到 GitHub。

### 本次 AI 协作任务

- 把营收增长从抽象概念细化成活动、分流、预算、指标和控制动作；
- 设计可复现的 A/B 实验分组；
- 处理并发预算、灰度、暂停和回滚；
- 明确 AI 运营 Copilot 的能力边界和安全护栏。

### AI 做了什么

- 创建 `docs/03-GROWTH-EXPERIMENT.md`；
- 设计 `DRAFT → REVIEW → GRAYING → ACTIVE → PAUSED/ROLLED_BACK/EXPIRED` 生命周期；
- 采用 `hash(campaign_id + user_id)` 稳定分流；
- 将预算真相优先放在 MySQL 条件更新，Redis 暂不承担预算最终一致性；
- 把订单事实、实验看板和活动控制分成不同边界。

### 人工判断与取舍

- 第一版不实现复杂推荐模型，只实现规则型分群和实验；
- 展示活动不预占预算，订单成功后再计入可靠消耗，避免展示链路和资金链路耦合；
- 回滚只影响未来新分流，不撤销历史订单和奖励；
- AI 只能生成候选草稿，发布权、预算权和账务权仍由规则系统与人工审批控制。

### 面试亮点

“回滚活动”与“回滚订单”不是同一件事：活动回滚控制未来流量，订单事实保持不可篡改。这体现了增长控制面和交易事实面的边界意识。

### 验收结果

增长实验文档已创建，包含生命周期、稳定分流、预算并发规则、护栏指标、回滚、指标闭环、AI 边界和测试用例。

### 下一步

进入 `2.2.1 Room、Order、Growth 服务边界`，开始服务接口、数据所有权和事件契约设计。

## Log 0005：服务边界和模块化单体取舍

日期：2026-09-02

### 用户反馈

用户确认继续推进；阶段性成果由用户手动 push 到 GitHub。

### 本次 AI 协作任务

- 将 Room、Order、Growth 三个领域落成服务边界；
- 明确 API、数据所有权、同步/异步通信和公共事件信封；
- 设计活动 offer 快照，避免订单在事务内同步依赖 Growth；
- 规划模块化单体到独立服务的演进路径。

### AI 做了什么

- 创建 `docs/04-SERVICE-BOUNDARIES.md`；
- 将 MySQL、Redis 和 Kafka 定义为共享基础设施，但不共享领域数据所有权；
- 规定 Growth 消费 Order 事件建立指标投影，而不是直接查订单表；
- 定义 `campaign_id/version/variant/rule/signature` 组成的不可变 offer 快照；
- 补充服务故障隔离矩阵和 Go 目录映射。

### 人工判断与取舍

- 第一版采用模块化单体，先验证业务和一致性，再按流量/团队边界拆进程；
- Order 不同步调用 Growth，保证活动服务故障不阻塞订单可靠受理；
- Growth 看板接受最终一致；
- 跨服务事件统一使用版本化信封，未知版本进入隔离队列。

### 面试亮点

“逻辑边界先于部署边界”是本项目的架构取舍：不是为了展示微服务而拆分，而是先把数据所有权和依赖方向做正确，再决定是否独立部署。

### 验收结果

服务边界文档已创建，包含服务职责、表所有权、API、事件、offer 快照、故障隔离和代码目录映射。

### 下一步

进入 `2.2.2 关键状态机`，把状态迁移规则统一并准备 Go 测试接口。
