## Log 0001：工作区初始化与面试导向设计

日期：2026-09-01

### 用户目标

用 30 天准备字节跳动后端开发实习生（营收增长方向）面试，重点补齐后端项目和 AI 工程能力，并让过程可复盘、可迁移。

### 本次 AI 协作任务

1. 反思原始准备思路是否过窄或不可行；
2. 检查空工作区和可操作文件范围；
3. 建立分层总体计划；
4. 建立项目、日志和上下文备份目录；
5. 执行第一个最低单元。

### AI 做了什么

- 判断“简历引导面试”方向可行，但必须以真实可验证实现为基础；
- 将项目收敛为直播营收增长平台，而不是无边界微服务集合；
- 定义最低单元：一次或少数几次执行、一个主题、明确产物和验收标准；
- 创建工作区文档和 Go 最小项目骨架；
- 探测本地 Go/Git 工具链。

### 人工判断与取舍

- 采用 `project/livegrow` 存放代码，`docs` 存放计划和设计，`records` 存放过程日志与上下文；
- 暂不引入真实外部服务和 API 密钥；
- 先完成订单可靠性主线，再扩展 AI Copilot 和多机房模拟；
- 所有规模指标必须通过本地压测获得。

### 本次亮点

“AI 生成活动候选配置，规则系统负责预算、权限、Schema、灰度和回滚”成为 AI 与后端营收业务的连接点。

### 验收结果

第一次 `go test ./...` 因默认 Go build cache 位于沙箱不可写目录而失败；将 `GOCACHE` 指向允许写入的临时目录后测试通过，`go run ./cmd/livegrow` 输出 `livegrow 0.1.0`。这被记录为环境约束，而不是代码缺陷。

### 可复用经验

AI 最适合辅助拆解、生成样板、补测试和比较方案；核心边界、风险判断、并发安全、一致性和最终验收必须由人负责。

### 下一步

完成 `2.1.1 直播营收业务范围`：一页需求、核心角色、主流程、非目标和成功指标。

### AI 做了什么

- 新增 `internal/platform/config`，支持环境变量、默认值、duration 和日志级别校验；
- 新增 `internal/platform/logging`，使用标准库 `log/slog` 输出 JSON；
- 新增 `internal/platform/apperrors`，分离客户端安全消息和内部错误原因；
- 新增 `internal/platform/httpserver`，统一 `ListenAndServe` 错误处理和 `Shutdown`；
- 更新 `cmd/livegrow/main.go`，加入 `/healthz` 和 SIGINT/SIGTERM 优雅退出。

### 人工判断与取舍

- 第一版只使用 Go 标准库，避免为了基础设施引入不必要依赖；
- 配置只负责进程级设置，业务配置留给后续领域层；
- 错误模型保留内部 cause，但不把敏感诊断直接返回给客户端；
- HTTP 集成测试没有强行绕过环境限制，先保留不依赖网络的 Shutdown 单测。

### 验收结果

- `GOCACHE=/private/tmp/livegrow-gocache go test ./...` 通过；
- 尝试运行 HTTP 进程时，监听 `:8080` 被当前沙箱禁止，日志明确记录 `operation not permitted`；
- 该失败被判断为环境约束，不是业务代码失败；完整监听和健康检查验证需在本机或 CI 环境补跑。

### AI 失败/风险记录

第一次 HTTP 服务测试尝试绑定本地随机端口，因沙箱网络权限失败。修正策略是将可验证部分拆成纯单元测试，并保留本机集成测试待办，而不是修改服务逻辑来迎合沙箱。

### 面试亮点

工程底座的关键不是“能启动一个 HTTP 端口”，而是统一配置、日志、错误和生命周期边界，让后续业务代码可以在一致的运行框架中演进。

### 下一步

进入 `3.1.2 HTTP API、请求校验和统一响应`，实现统一响应格式、请求 ID 和业务无关的 HTTP 处理层。

## Log 0010：HTTP API 传输层

日期：2026-09-04

### 用户反馈

用户确认继续推进工程环节。

### 本次 AI 协作任务

- 实现请求 ID 中间件；
- 实现结构化访问日志；
- 实现统一成功和错误 JSON 响应；
- 实现严格 JSON 解码和可复用请求校验；

### AI 做了什么

- 新增 `internal/platform/httpapi`；
- 支持复用合法 `X-Request-ID`，对缺失或不安全值生成新的随机 ID；
- 使用 `Response`/`Error` 信封统一返回 `data`、`error` 和 `request_id`；
- 将未知 JSON 字段、多 JSON 值和非法请求映射为客户端安全错误；
- 用 `Validator` 接口让领域请求自行提供校验规则。

### 人工判断与取舍

- 请求 ID 只接受安全字符，避免把任意 Header 内容写入日志；
- 错误响应只暴露稳定错误码和安全消息，内部 cause 保留给日志或上层处理；
- 严格 JSON 解码有利于尽早发现客户端拼写错误，但未来兼容旧客户端时需要显式评估；
- 传输层不包含业务规则，避免 HTTP handler 直接操作订单或数据库。

### 验收结果

- `GOCACHE=/private/tmp/livegrow-gocache go test ./...` 通过；
- `GOCACHE=/private/tmp/livegrow-gocache go vet ./...` 通过；
- httptest 覆盖请求 ID、错误脱敏、JSON 解码、参数校验和访问日志状态记录。

### AI 失败/风险记录

初版错误响应实现曾先写入成功响应再尝试替换错误体，这在 HTTP 已发送 Header 后不可行。修正为统一走 `WriteAppError`，并增加响应体断言测试。

### 面试亮点

传输层统一了请求追踪、错误契约和输入边界，使领域服务不需要重复处理 HTTP 细节；请求 ID 还能把一次请求串联到后续 Kafka 事件和日志中。
