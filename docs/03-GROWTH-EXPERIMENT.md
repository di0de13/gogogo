# 营收增长实验设计

版本：v0.1  
日期：2026-09-02  
对应计划：`2.1.3 增长实验场景`

## 1. 目标

Growth Service 负责把运营目标转化为可控的活动规则，并将用户分流、预算消耗和营收结果连接起来。第一版重点体现三个能力：

1. 同一用户在实验周期内稳定进入同一分组；
2. 活动预算不会因为并发请求被超发；
3. 活动可以灰度、暂停、回滚，且不会修改已经发生的订单事实。

## 2. 活动对象

一个活动（Campaign）包含：

- `campaign_id`：全局唯一 ID；
- `name`、`description`；
- `region_allowlist`：允许的国家/地区；
- `user_segment`：新用户、活跃用户或规则组合；
- `room_allowlist`：可选的直播间范围；
- `start_at`、`end_at`；
- `currency`、`total_budget`、`per_user_budget`；
- `variants`：实验分组及流量比例；
- `reward_rules`：礼物、折扣或奖励规则；
- `version`：发布版本；
- `status`：生命周期状态；
- `created_by`、`approved_by`、审计时间。

活动发布后，版本内容不可原地修改；修改必须创建新版本或新活动，保证实验期间规则可复现。

## 3. 活动生命周期

```text
DRAFT → PENDING_REVIEW → APPROVED → GRAYING → ACTIVE
                                  ├→ REJECTED
                                  └→ PAUSED → ACTIVE
                                           └→ ROLLED_BACK
ACTIVE → EXPIRED
```

状态规则：

- `DRAFT`：运营或 AI 生成的草稿，只能编辑，不能对用户生效；
- `PENDING_REVIEW`：已通过格式和业务校验，等待人工审核；
- `APPROVED`：审核通过，等待定时生效或灰度；
- `GRAYING`：小比例流量生效，持续观察护栏指标；
- `ACTIVE`：达到配置流量，正常运行；
- `PAUSED`：暂时停止分配新用户，保留历史实验数据；
- `ROLLED_BACK`：因异常回滚，不允许直接恢复原版本；
- `EXPIRED`：超过结束时间，停止新分流。

非法迁移必须拒绝并记录审计日志，例如 `DRAFT → ACTIVE`、`ROLLED_BACK → ACTIVE`。

## 4. 用户分群和稳定分流

### 4.1 资格判断

请求上下文至少包含：`user_id`、`region`、`room_id`、当前时间和必要的用户标签。

资格判断顺序：

1. 活动状态和时间窗口；
2. 地区白名单；
3. 直播间白名单；
4. 用户分群条件；
5. 预算和单用户额度；
6. 实验分组分流。

### 4.2 稳定分流算法

使用稳定哈希，不使用随机数：

```text
bucket = hash(campaign_id + user_id) % 10000
```

按照累计流量比例映射到 `control`、`variant_a`、`variant_b` 等分组。同一用户在同一活动版本下重复请求得到相同分组；活动版本改变时可以重新分流。

分组结果可写入 `assignments` 表或缓存，但真实来源由 `campaign_id + version + user_id` 决定，避免缓存丢失造成分组漂移。

## 5. 预算控制

### 5.1 两级预算

- 活动总预算：所有用户累计消耗不能超过 `total_budget`；
- 单用户预算：单个用户累计消耗不能超过 `per_user_budget`。

金额使用整数最小货币单位保存，不使用浮点数。

### 5.2 并发安全

预算扣减必须是原子条件操作，不能采用“先查询余额，再单独更新”的非原子流程。原型可以使用：

- MySQL 条件更新：`used_budget + cost <= total_budget`；
- Redis Lua 做快速预占，再异步落库；
- 或先在数据库中完成可靠扣减，再更新缓存。

第一版优先使用 MySQL 条件更新，保证语义清楚；Redis 只做缓存和限流，避免双写预算带来额外一致性问题。

### 5.3 预算预占与释放

如果活动在用户查看时就锁定预算，需要定义预占过期时间；如果只在订单成功后计入消耗，则可能出现“展示有优惠但下单时预算已用尽”。第一版采用：

- 活动展示只返回预计可用，不预占；
- 订单成功事件到达后，按订单金额或奖励成本原子增加已用预算；
- 超预算的订单不回溯修改，活动通过护栏和并发扣减避免继续发放；
- 预算扣减失败时，记录异常事件并暂停相关奖励动作。

## 6. 灰度、护栏和回滚

### 6.1 灰度过程

1. 审核通过，流量比例为 0%；
2. 设置 1% 或测试用户灰度；
3. 观察错误率、订单成功率、奖励成本和转化率；
4. 达到阈值后逐步扩大比例；
5. 任一关键指标异常，自动暂停新分流。

### 6.2 护栏指标

第一版关注：

- 订单失败率；
- 重复扣币或重复发放计数；
- 单用户奖励成本；
- 活动预算消耗速率；
- 实验组与对照组的转化率差异；
- 消费延迟和死信数量。

护栏指标用于控制活动，不直接篡改订单和营收事实。

### 6.3 回滚语义

回滚只停止未来的新分流：

- 已创建订单继续按照订单领域规则完成或补偿；
- 已发放奖励不撤销；
- 新请求不再命中被回滚版本；
- 生成回滚审计事件，记录操作者、原因和指标快照。

## 7. 营收指标闭环

Growth Service 不直接查询订单数据库中的每个请求，而是消费可靠的营收事件：

```text
Order Service
    ↓ ORDER_CREATED / GIFT_FULFILLED / REVENUE_RECORDED
Kafka
    ↓
Growth Metrics Consumer
    ↓
按 campaign_id、version、variant、region 聚合
    ↓
实验看板和护栏判断
```

指标聚合允许最终一致，但必须满足：

- 消费者幂等；
- 事件包含活动版本和实验分组快照；
- 订单事实与实验指标可以通过 `order_id` 追溯；
- 聚合失败可重放，不影响订单主链路。

## 8. AI 运营 Copilot 边界

### 8.1 AI 可以做什么

- 根据自然语言生成活动草稿；
- 推荐用户分群和实验变量；
- 解释历史指标和异常趋势；
- 生成活动测试用例和风险检查清单。

### 8.2 AI 不能做什么

- 直接发布活动；
- 绕过地区、权限或预算校验；
- 修改订单、账户和营收事实；
- 自行扩大灰度比例；
- 删除审计记录。

### 8.3 结构化护栏

```text
自然语言需求
  ↓
AI 输出 JSON 草稿
  ↓
Schema 校验
  ↓
枚举、时间、地区和金额范围校验
  ↓
预算模拟与历史指标检查
  ↓
人工审批
  ↓
灰度发布
```

AI 输出必须携带 `prompt_version`、`model`、`generated_at` 和人工修改记录，便于复盘；这些元数据不能替代业务审计。

## 9. 测试用例

- 草稿不能直接命中用户；
- 未审核活动不能发布；
- 地区不匹配的用户不能获得活动；
- 同一用户在同一版本内重复请求得到同一分组；
- 不同版本可以重新分组；
- 并发订单不能突破活动总预算；
- 单用户累计奖励不能超过个人预算；
- 灰度比例为 0 时无新用户命中；
- 暂停或回滚后新请求不再分流，历史订单不受影响；
- 重复营收事件不会重复增加实验指标；
- 指标消费者停止后恢复可以从 Kafka 重放；
- AI 输出非法金额、地区或字段时被拒绝。

## 10. 面试叙事

### 30 秒版本

增长服务把活动配置、稳定分流、预算约束和营收指标连接起来。同一用户通过活动版本和用户 ID 做稳定哈希，避免实验漂移；预算用数据库条件更新保证并发下不超发；活动经过审核后先灰度，异常只停止未来分流，不修改已经发生的订单。AI 可以生成活动草稿，但不能绕过规则和审批。

### 关键取舍

- 为什么用稳定哈希而不是随机分流：保证重复请求和跨服务读取的一致性；
- 为什么第一版不用 Redis 直接做预算真相：避免缓存和数据库双写的一致性复杂度；
- 为什么回滚不撤销已发奖励：订单事实和活动控制是两个边界；
- 为什么营收指标异步聚合：看板允许延迟，但不能阻塞订单主链路。
