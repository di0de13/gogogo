# LiveGrow 业务需求与范围

版本：v0.1  
日期：2026-09-02  
对应计划：`2.1.1 直播间和用户场景`

## 1. 文档目的

本文件为后续数据库、API、消息事件、测试和面试讲解提供唯一的业务基线。项目是面向面试准备的可运行原型，不代表真实线上系统，也不接入真实支付、真实用户或真实 TikTok 内部数据。

## 2. 业务目标

LiveGrow 面向直播平台的营收增长场景，打通以下闭环：

```text
用户进入直播间
    ↓
读取直播间和用户可参与的活动
    ↓
用户购买虚拟礼物
    ↓
订单可靠落库并产生营收事件
    ↓
异步更新增长指标
    ↓
运营根据实验结果调整活动
```

第一版关注“核心链路可靠、增长规则可控、故障可解释”，不追求功能数量。

## 3. 用户与系统角色

| 角色 | 主要动作 | 权限边界 |
|---|---|---|
| Viewer 观众 | 进入直播间、查看活动、购买礼物 | 只能操作和查询自己的订单；不能修改活动 |
| Creator 主播 | 查看直播间状态和营收概览 | 只能查看自己有权限的直播间 |
| Operator 运营 | 创建活动、配置人群、发起灰度、查看实验指标 | 不能直接修改订单、余额和账务状态 |
| Risk/Reviewer 风控或审核人 | 审批高风险活动、暂停活动、触发回滚 | 只能执行审核和控制动作 |
| Platform 系统 | 路由、幂等、写库、投递事件、重试、对账 | 关键状态变更必须经过领域服务和规则校验 |

## 4. 核心场景

### 4.1 进入直播间

观众携带 `user_id`、`room_id` 和 `region` 请求直播间详情。系统返回：

- 直播间基本信息；
- 当前热度和在线人数（允许短暂延迟）；
- 该用户可见的活动摘要；
- 礼物目录摘要。

热点直播间是读流量主要来源，后续使用 Redis 缓存和热点保护；不存在的直播间需要避免缓存穿透。

### 4.2 购买虚拟礼物

观众提交 `user_id`、`room_id`、`gift_id`、数量、币种和客户端幂等键 `idempotency_key`。

系统需要：

1. 校验用户、直播间、礼物和地区规则；
2. 创建唯一订单；
3. 在本地事务中写入订单及待投递的营收事件；
4. 返回可查询的订单结果；
5. 异步完成礼物发放、营收统计和活动指标更新。

本项目中的“扣币/支付”使用可控的模拟账户服务，不连接真实支付渠道。

### 4.3 配置营收增长活动

运营可以配置：

- 目标地区或用户分群；
- 活动开始和结束时间；
- 礼物或奖励规则；
- 单用户预算上限和活动总预算；
- A/B 实验分组比例；
- 灰度比例和暂停条件。

活动需要经过 Schema、权限、预算、时间和规则检查。AI 可以生成候选配置，但不能绕过校验、审批或直接修改订单与账户。

### 4.4 查看营收指标

系统提供两类指标：

- 账务事实：订单金额、支付结果、礼物发放结果，必须可追溯、可对账；
- 运营指标：实时 GMV、参与人数、转化率、实验分组表现，允许秒级到分钟级延迟。

两者不强行使用相同的一致性等级。

## 5. 核心业务流程

### 5.1 直播间读取

```text
Gateway → Room Service → Redis
                         ├─ 命中：返回缓存
                         └─ 未命中：MySQL → 回填 Redis → 返回
```

缓存不可用时，允许降级为受保护的数据库查询；不能因为热度看板不可用而阻塞订单创建。

### 5.2 礼物订单

```text
请求
  ↓
幂等键检查
  ↓
MySQL 本地事务：订单 + Outbox 事件
  ↓
返回订单已受理
  ↓
Outbox 投递 Kafka
  ↓
消费者幂等处理：扣币模拟 / 发礼物 / 更新营收指标
  ↓
失败重试 → 死信 → 对账补偿
```

第一版订单接口的语义是“可靠受理”，不是同步保证所有下游动作已经完成。客户端通过订单查询获得最终状态。

### 5.3 活动发布

```text
运营或 AI 草稿
  ↓
结构化解析和 Schema 校验
  ↓
权限、地区、时间、预算和规则校验
  ↓
人工审批
  ↓
小流量灰度
  ↓
指标观察 / 异常自动暂停
  ↓
扩大流量或回滚
```

## 6. 一致性等级

| 数据/动作 | 一致性要求 | 原因 |
|---|---|---|
| 订单唯一性 | 强约束 | 不能因重试生成重复订单 |
| 模拟账户扣币 | 强约束、可幂等 | 不能重复扣减 |
| 礼物发放 | 最终一致、可补偿 | 下游失败可重试，必须可追踪 |
| 营收事实事件 | 至少一次投递 + 幂等消费 | 不能静默丢失 |
| 热度、在线人数 | 最终一致 | 实时性优先于精确账务 |
| 实验看板 | 最终一致 | 允许异步聚合 |
| 活动配置 | 发布后版本固定 | 避免实验过程中规则漂移 |

## 7. 第一版成功指标

这些是本地原型的验收指标，不是生产承诺：

- 重复提交同一幂等键不会创建第二个订单；
- 模拟 Kafka 重复投递不会重复扣币、发礼物或累计营收；
- MySQL 提交成功后，即使投递器暂时停止，Outbox 事件仍可恢复投递；
- 消费连续失败后进入重试或死信路径，并可通过对账任务发现；
- 直播间缓存命中、未命中、缓存故障三种路径均有测试；
- 订单主链路有单元测试、集成测试和至少一次故障演练；
- 所有压测数字记录运行环境、参数和日期。

## 8. 明确不做的事情

- 真实支付渠道、充值渠道和汇率结算；
- 真实 TikTok 用户、主播、礼物或内部接口；
- 真实全球多机房部署；本项目只做 region 逻辑模拟和故障演练；
- 复杂推荐模型和实时风控模型；
- 完整运营后台前端；使用 API、配置文件或简单管理命令代替；
- 直接让大模型决定金额、权限、账务或发奖结果。

## 9. 面试叙事提炼

### 30 秒版本

我做了一个面向直播营收增长的 Go 服务原型，覆盖直播间读取、虚拟礼物订单、营收事件和活动实验。核心是用本地事务加 Outbox 保证订单事件可靠落库，再通过 Kafka 异步解耦下游处理，并用幂等消费、重试、死信和对账处理最终一致性。AI 只生成候选活动配置，真正的预算、权限和灰度由规则系统控制。

### 可被继续追问的技术点

- 为什么订单接口返回“已受理”而不是同步完成；
- 如何处理 MySQL 成功但 Kafka 失败；
- 如何避免 Kafka 重复消费导致重复扣币；
- 为什么热度指标可以最终一致而账务事实不能；
- 为什么 AI 不能直接修改营收状态；
- region 如何进入缓存 key、数据库记录和消息事件。
